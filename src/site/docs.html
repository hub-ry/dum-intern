How it works

Dum is a small intern you teach. You learn one idea, explain it in your own words, and Dum turns your explanation into a creation you can read back. This page describes what exists today, nothing more.

What's public and what isn't

Dum's workshop runs on its owner's machine, a host we call the hub. That's where lessons, teaching and creations live. It isn't open to the public, and this site has no login or workshop prompts.

What you can read here is the project itself and one verified example creation. The example came from sample teaching about loops and conditions. It shows what Dum produces. It isn't a record of anyone's learning progress.

Lessons

The guided lessons are deliberately small, and there are only a few right now:

  • Visiting every item with for...of
  • Choosing with if and else
  • Loops and conditions together

Materials and reasoning exercises sit together in the study zone. Predict a result, check it, and try again with another example; writing syntax is optional. You can record other teaching too, but the guided path is these three ideas.

The loop

  1. Study Read one short lesson on one idea.
  2. Try it Predict what happens in the study zone, inspect the feedback, and try again.
  3. Teach Dum Write down the idea in your own words. This text is what gets sent to the model.
  4. Creation Dum builds a small, self-contained interactive page from your teaching, then verifies it.
  5. Correction Explain what to change and request another build. A revised version never replaces the original; failed verification stays visible.
  6. Revisit Come back later and read the creation again. Every job has a stable deep link in the private workshop.

What a creation is

A creation is a self-contained HTML page generated from your teaching and goal context, with output constrained by a JSON schema. The host never executes its JavaScript. An isolated browser verifier exercises it and captures screenshots. The reader pairs those images with captions and matching source excerpts. In the private workshop, you can also use the demo inside a sandboxed frame on a separate origin.

The public example is exactly this: six screenshots from the corrected creation of one job, with the captions and code the backend recorded. Reading saved pages makes no model calls.

Verification

Each creation is checked with a browser automation script inside an isolated Docker container. The container has no network, a read-only filesystem and no privileges. The script performs the declared clicks and input changes and compares what it sees with what the creation claims. The screenshots you read were captured during that run.

This isolation is about offline execution and keeping generated code away from the host. It's not a universal security guarantee, and the generated page should still be treated as untrusted code.

Runtime

The workshop uses Node 24, TypeScript, tsx, and zod. Its default local setup listens on two separate origins:

  • 127.0.0.1:8770 serves the workshop app and its API, with authentication whenever a token is set.
  • 127.0.0.1:8771 serves finished artifacts, such as screenshots and the creation's own page, from a separate origin so they can't touch the app.

Private-network access requires a workshop token. Neither port is exposed by this public site. The public site uses a separate, dependency-free static server.

Model access

Builds use the Claude Code command line tool with an authenticated subscription. It's invoked in print mode with no tools, no hooks and no MCP servers, and asked for output matching a strict JSON schema. With that setup no API key is required. The example creation was generated by claude-fable-5-1. Teaching Dum doesn't retrain any model.

Privacy

  • Lessons, teaching text, job history and creations stay on the hub.
  • Generation sends private inputs to the configured Claude CLI provider. See the workshop privacy and execution boundaries for what is sent.
  • Verification runs offline in the container.
  • Reading saved creations, here or in the workshop, makes no model calls.
  • No account is needed to read this site. The jumping game keeps no score history. Cloudflare handles public delivery.

Schedules

A goal can have an optional interval schedule. It queues new creations from your existing teaching while the hub is running, even when your laptop is closed. Scheduled builds use the model just like manual builds. Leave scheduling off to build only when you press Build now.

Code and the full history of changes are in the source repository. For the thinking behind the learn-then-teach order, see the philosophy page.
