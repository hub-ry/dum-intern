Docs

Dum is a Mac app that stays on in the menu bar. It follows what you're learning across a tree of zones, keeps track of the skills you've shown you have, and writes code when you ask, but only with those skills. The point is that you could take the AI away and still understand the architecture, start implementing, and ask precise questions.

Two characters talk to you. Dum is the intern you work with. The Wizard is the advisor who speaks up now and then.

Getting started

See installation. Dum needs macOS 13 or later. Voice needs macOS 14 or later on Apple Silicon; everything else works from the keyboard on Intel too.

Dum has no Dock icon. It lives in the menu bar, where its icon is Dum's own face. The menu has Ask Dum…, Open Panel, Switch Zone, Start Voice, Send Draft, Pause the Look and Quit Dum.

On first launch Dum asks What are you trying to learn? Type an answer or say it. It becomes your first zone: the answer is the zone's goal, and its first 80 characters are the name, which you can change later. Nothing is sent to a model for this.

Because the look is on by default, macOS asks for Screen Recording permission the first time Dum starts. You can say no; see the look for what changes.

Next, Dum needs someone to power it. A banner says Dum isn't powered yet with a Who powers Dum? button. Zones, skills, notes and commands like :tree work without a backend. Messages to Dum, :projects and :submit don't. If you send a message first, it stays in the box until you've picked one. See who powers Dum.

Zones

A zone is something you're learning, like Programming › Data Structures. It's not a folder or a Git repository. Zones are the only scope Dum has.

  • Each zone has a name, a goal in your words, and an optional language. Leave the language empty and the zone uses its parent's.
  • Zones nest, up to 16 levels deep. Names must differ between siblings.
  • The Zones tab has New zone, and for the selected zone Enter, New zone inside, Edit and Delete. There's no way to move a zone to a new parent.
  • The Context tab holds Notes for this zone: background Dum reads in this zone and the zones inside it, up to 16 KiB per zone. Notes are context. They never unlock a skill or give Dum access to a file.

Entering a zone makes it the active context. Do it from the Zones tab, with ⌘K in the command bar, or from Switch Zone in the menu bar. Switching stops whatever Dum was doing in the old zone. Earlier conversation in the new zone comes back as history; a question Dum asked last time isn't waiting for an answer any more.

A zone inherits its ancestors' goals, nearest language and notes, up to 64 KiB of notes in total, keeping the nearest zones first. It doesn't inherit their conversation, memory, suggested projects, change history or followed folders. Those belong to one zone. Your skills belong to none: there's one tree, and a skill you prove in one zone counts in all of them.

Deleting a zone also deletes the zones inside it. Your skills, memory notes and evidence stay, and the zone's files stay on disk in ~/.dum/zones/ for you to look at.

Skills and evidence

Your skills are plain Markdown files in ~/.dum/skills/, one per skill. You can read, edit or delete them; they open in Obsidian. A skill is scoped to a language or to none, so printing in Python doesn't count in Go.

The Skills tab shows curated tracks: basics for C, C++, Go, Java, JavaScript, Python, Rust and TypeScript, plus graphics, interview, systems and a language-free builder track. Each skill shows as built, recognized, open (everything under it is built) or locked. Skills you add that aren't on a track still get up to three mapped prerequisites.

Recognize, build, apply

  • Recognize. You explained what the skill is and what it's for, in your own words. Dum quotes the sentence it's crediting, and the quote has to come from your message in that request. Its prerequisites have to be recognized too.
  • Build. You wrote it yourself, unaided. Share the files, Dum reviews them, then asks whether you wrote them yourself without AI or copied code. Only y or yes records the build; anything else keeps the review and records nothing. When you hand in a suggested project, the --unaided flag is that yes. A build also needs its prerequisites built.
  • Apply. You built it and then reasoned about when and why to use it. The same reasoning without a build only records recognition.

Screens, files Dum reads, suggestions, memory, zone notes and code Dum wrote never count as evidence. A saved file doesn't prove you wrote it; your own yes does, and it can be wrong. Reviews are model judgments, so check them.

You can also add a skill you already have with :skill name or :skill name in python. That records a self-report that you can write it unaided, and it isn't reviewed. :skill -name takes a skill off the tree.

The gate

The gate decides what Dum may write for you. It's checked in code, not just asked of the model. Concepts (language features, data structures, algorithms) need build. Tools (one library, framework, API or command) need recognize. Skills on a curated track always count as concepts. Every prerequisite under a skill has to hold too, so if you take an early rung back, the skills that rest on it lock again, though their notes stay.

The Boundary tab, or :boundary, shows what Dum may do right now: what it may write, what it may use as a tool, what's closed, and which files it may read and change.

"not yet"

If Dum just credited you with something you don't think you've earned, say not yet, or not yet recursion to name the skill. The skill goes back to where it was, and Dum holds it there across zones and restarts. Only a reviewed unaided build or a :skill self-report lifts the hold.

The strip at the top of the panel reads newbie, intern, good and cracked at 0, 8, 24 and 64 built skills with their prerequisites intact. Messages and recognition don't move it. It's a joke label, not a rating.

Talking to Dum

There are three surfaces, all sharing one conversation and one draft per zone.

  • The panel has the tabs: Conversation, Zones, Skills, Memory, History, Context, Evidence, Boundary, Suggested projects, Changes and Settings. Closing it hides it.
  • The command bar opens with ⌘⇧D in the middle of the screen your cursor is on. Type a message or a command, see the latest reply, switch zones with ⌘K, or jump to a panel tab. Esc closes it and gives focus back to the app you were in. Your draft stays.
  • The bubble appears near your cursor when you use voice. It shows what you said and Dum's reply. You can't click it; clicks go through to whatever is under it.

Voice

Hold ⌃⌥Space and talk; let go to stop. Speech is turned into text on your Mac by a bundled copy of OpenSuperWhisper, set up under Set up voice in Settings, where you allow the microphone and pick a language and a speech model. The text lands in your draft. It never sends itself. The bubble shows it for 20 seconds; press ⌘⇧↩ to send it, or open the command bar to edit it.

  • Voice won't start over a draft that isn't empty. Send it, edit it or clear it first.
  • A recording stops after two minutes and is thrown away.
  • The audio is a temporary file, deleted when transcription finishes or fails.
  • You can also start and stop voice with the Voice button or the menu bar.
  • Voice comes with the packaged app on Apple Silicon. Running Dum straight from a checkout with npm run desktop has no voice.

Keyboard only

Everything works without the mouse.

  • Return sends, Shift-Return adds a line, ⌘. stops Dum.
  • Esc backs out one step: it closes an open chooser first, then the command bar. In the panel it goes back to Conversation, then hides the panel. It never stops Dum or answers a question.
  • Panel tabs: arrow keys move, Home and End jump, Return opens.
  • Zone tree: Up and Down move, Right and Left open and close, Return enters, F2 edits.
  • The ⌘K switcher filters as you type.
  • The three global shortcuts (command bar, hold to talk, send the draft) can be changed in Settings. Each needs ⌘, ⌃ or ⌥.

Sharing

Dum can't see your files unless you show it. Share in the message box offers A file…, A folder…, Type a path… and A screen or window…. A typed path still needs your confirmation in a macOS dialog. A share lasts for one message: once Dum finishes answering, it can't read the files again. Text it already read stays in the conversation. A share you don't send expires after five minutes. For a folder Dum should keep seeing, follow it.

A screenshot is previewed before you send it. It goes once to the helper model, and only the helper's text description goes into the conversation. Dum doesn't save it to disk.

Commands

  • :tree or :skills: your skill tree.
  • :inspect file or :inspect file:10-40: show Dum a file you shared or follow.
  • :projects: suggested projects.
  • :submit p1 file --unaided: hand in your work on a project.
  • not yet: undo the skill just recorded.
  • :skill x, :skill -x: add or remove a skill.
  • :memory, :remember note: this zone's notes.
  • :context: the personal background used for suggestions.
  • :evidence: what each skill rests on.
  • :boundary: what Dum may do right now.
  • :log: everything said in this zone.
  • :help: this list.

Mode in Settings is understand or anti-vibe. Both use the same gate. Anti-vibe asks for your approach first, then Dum does the unlocked parts.

Voice, giving focus back to your previous app, and the bubble floating over full-screen apps use macOS APIs that haven't been tried on a real Mac yet.

Changes

Ask Dum to change a file and, if you hold the skills, it writes the change straight into the file. There's no yes/no step. You see the diff afterward, with a Revert button.

  • Dum only writes files you shared with the message or that sit in a folder you follow in this zone. A new file can only go inside a shared or followed folder.
  • Each change names the skills it uses. If one is locked, nothing is written and Dum says which skill and why.
  • Dum reads a file before changing it, and writes only if the file is byte-for-byte what it read. If you saved in your editor since, the change is refused and Dum reads it again. It never writes over a save it hasn't seen.
  • A new file is never created over one that appeared in the meantime. Yours is kept.

The diff shows in the conversation, and the Changes tab lists every change in the zone, newest first. Revert puts the file back the way it was, or deletes a file Dum created. It works after the share has ended. If you've edited the file since Dum wrote it, Revert refuses and your edits stay.

Each change is kept in ~/.dum/zones/<zone>/changes/ with the file before, after, and the full patch. open the change record opens the patch.

Dum doesn't run your programs, tests or builds. Run them in your own terminal.

The look

Dum is always on. While you're in a zone it looks every 3 seconds, without a model, and calls a model only when something changed. It never reads keystrokes, the clipboard or your editor's unsaved text.

What it reads every 3 seconds

  • Apps: which app is in front, its name and window number. Not window titles.
  • Screen: a 320-pixel-wide image of the display your cursor is on, shrunk to a 64 × 40 grid of gray levels and compared with the last one. Only the number of changed cells leaves the main app process. The image isn't kept or saved.
  • Followed folders: whether any file's size or timestamps changed. A file that changed is read in full. New files are picked up about every 15 seconds.

While a Dum window has focus, the app and screen are ignored.

What makes it call a model

  • You saved, added or removed a file in a followed folder, and it stayed quiet for two looks.
  • You switched apps or windows and stayed for two looks.
  • The screen was busy for a bit, then went still.

The call goes to the helper model and the Wizard answers, or stays quiet. If you switched apps or the screen settled, the screen look is on and the helper can see pictures, Dum sends one 1280-pixel-wide frame of the screen with it. A saved file sends the diff, not a frame. The Wizard may also keep one short note in the zone's memory.

The caps

  • At most 40 calls an hour, and one at a time.
  • At least 30 seconds between any two calls; a minute between file triggers, 90 seconds between screen triggers, two minutes between app triggers.
  • The same app window doesn't trigger again for 10 minutes.
  • Up to four file diffs and 96 KiB per call. A frame over 3.75 MB isn't sent.
  • No calls while Dum is answering you or waiting on your answer.

Screen look and permission

Settings → Look has two switches, Apps and Screen, both on in a new install. The screen look needs macOS Screen Recording permission, which macOS asks for on first launch. If you say no, Dum looks at app switches and saved files only, until you allow it under Screen Recording settings.

Pausing

Pause from the menu bar (Pause the Look), the looking pill at the top of the panel, or Settings. It stays paused until you resume or restart Dum. The look also stops while you're recording voice and while the Mac sleeps or is locked.

Followed folders

Settings → Followed folders → Follow a folder… picks a folder for this zone. Dum may read the saved files in it, notices when you save, and can write changes there. Up to eight folders per zone.

  • Only text files up to 256 KiB are read, up to 2,000 files per folder.
  • Hidden files and folders are skipped, which includes .git and .env, and so are node_modules, dist, build and target.
  • Credential-looking files are skipped: SSH keys, .pem and .key files, token and secret files, and the like. That's by name; a secret pasted into an ordinary source file isn't detected.
  • Your home folder, the whole disk, system folders and ~/Library can't be followed.

Without a backend Dum still watches, and the status says advice needs a backend.

Noticing app switches and the Screen Recording prompt use macOS APIs that haven't been tried on a real Mac yet.

Suggested projects

Dum doesn't run courses or quizzes. When you want practice it suggests projects that fit a skill's scope and your zone.

  • :projects new suggests projects for this zone; :projects recursion sizes them to one skill. Add in go for a language. The Skills tab has a suggest projects button on each skill.
  • Each project says what done means, roughly how many active hours it takes, how hard it is, why it fits, and an ordered list of milestones, prerequisites first.
  • Projects are sorted by estimated time, then difficulty. A second model call checks each one covers what it claims; up to four come back.
  • Suggestions use the zone's goal and notes, your tree, the zone's memory, and your personal context file if you turned it on in Settings.
  • :projects start p1 marks one you're working on. The Wizard keeps its asides to itself until you :projects stop or pass every milestone unaided.
  • :submit p1 main.go --unaided hands in your work, as does Hand it in in the Suggested projects tab. Each milestone is reviewed on its own, in prerequisite order. Without --unaided, or the I wrote this myself box, you get the review but no build credit.

Choosing or starting a project unlocks nothing. Time estimates are model guesses.

The Wizard

The Wizard is the advisor. It speaks up during a conversation when it suspects a concrete mistake, at most once per request, and after the look notices something. Most of the time it says nothing.

When it cites something, the claim and the link come from a fixed catalog of primary sources: Git, SQLite, Python, Node and Effective Go docs, the Rust Book, cppreference, MDN and the HTTP RFC. Its own sentence passes a word screen that drops dates, statistics, quotes, unsourced names and claims about what everyone does. The screen is a filter, not a fact-checker. If no source fits, the Wizard stays quiet.

Who powers Dum

Who powers Dum? picks the backend and two models: Dum's model for the conversation and the Helper model for the Wizard, the look, screenshots and project suggestions. Both come from the same backend. Change them later under Settings → Agent.

Backends

  • Claude. Public builds connect with your own Anthropic API key. Local builds can also Sign in with Claude and use a Claude subscription. Defaults are claude-opus-5-5 for Dum and claude-fable-5-1 for the helper, both at high effort. Dum ships with its own Claude Code, so you don't install anything.
  • On this Mac. Models you run in Ollama or LM Studio. Dum installs neither. It finds them on 127.0.0.1 (ports 11434 and 1234) and won't talk to any other address. Ollama cloud models are refused. LM Studio models are text-only in Dum, so they can't look at the screen.
  • ChatGPT. Sign-in with your ChatGPT account is built, but it's switched off in current builds.

Model lists come live from the backend. Dum's model has to support function calling. If the helper can't see pictures, the screen look and shared screenshots don't work with it. Models Dum hasn't been verified with are marked untested; so far that's every model but the two Claude defaults.

There's no fallback. If the backend you picked fails, Dum tells you; it never quietly switches to another one.

Build flavors

Every build is public or local, fixed when it's built. A public build follows each provider's rules: Claude only with an API key, never subscription sign-in. A local build, which you make from source for yourself, may also sign in with a Claude subscription. npm run desktop and npm run desktop:mac-local make local builds; npm run desktop:mac makes the public Mac app.

Your API key is encrypted with Electron's safe storage, which uses the macOS Keychain, and kept in Dum's app data, never in settings. Subscription sign-in is handled by the bundled Claude Code, and signing out there also signs Claude Code out on your Mac.

Key encryption and subscription sign-in haven't been tried on a real Mac yet.

Privacy

What stays on your Mac

  • Your skill tree, zones, conversations, memory, evidence, suggested projects and change records, all as plain files in ~/.dum/.
  • Settings and the encrypted API key, in Dum's app data folder.
  • Voice: audio and transcription never leave the Mac.
  • The look's routine screen samples. Only frames sent with a model call leave, and none are saved.

What goes to the backend

Your messages, the zone's goal and notes, your skills and boundary, recent conversation, and the text of files Dum reads from shares and followed folders. For the look: the front app's name, diffs of saved files, and sometimes a screen frame. For suggestions: your personal context file, if you turned it on.

  • Claude: sent to Anthropic, through Claude Code, under your API key or subscription.
  • On this Mac: sent only to Ollama or LM Studio on 127.0.0.1. Dum can't control what that server does next, so check its settings if it can reach the internet.

The web tree is off unless you link it under Settings → Web tree. Then only your skills and removals go to that server: no zones, conversations, holds or files. Anyone with the link can see and edit the tree there.
